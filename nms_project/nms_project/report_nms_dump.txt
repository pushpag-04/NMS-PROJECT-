ABSTRACT 
Modern enterprise and communication infrastructures provide high-speed, distributed 
connectivity across numerous interconnected endpoints, servers, routers, switches, and access 
points. These capabilities enable scalable operations but also significantly heighten the demand 
for continuous network topology discovery, device role mapping, and automated threat 
defense. Large traffic volumes, complex multi-tier topologies, and dynamically configured 
endpoints make manual identification of deceptive nodes and network pathways difficult. 
This project presents NetMap AI, a lightweight web-based Network Management 
System that generates multi-tier network topologies, supports interactive manual network 
design, and verifies device roles with an explainable machine-learning model. Eight features 
are used as input: connection count, neighbor router count, neighbor switch count, neighbor 
endpoint count, gateway connectivity, open port count, traffic throughput, and packet 
forwarding rate. A Weka J48 Decision Tree classifies each device into one of six roles: Internet 
Gateway, Router, Switch, Server, Access Point, and Client (PC). The implemented model 
achieves an overall accuracy of 98.2% on the simulated topologies used in this project. 
After classification, the system reports a prediction confidence and compares the 
predicted role with the configured device type, marking each device as Matched or Refined so 
that rogue or misconfigured devices can be identified. The backend is built with Spring Boot 
and Java, all topology data is held in thread-safe in-memory collections so that no external 
database is needed, and the Cytoscape.js dashboard provides interactive visualization of 
networks of 5 to 50 devices. 
The project demonstrates an integrated prototype combining automated topology 
generation, manual graph design, AI-based role mapping, and dashboard visualization. The 
design can be extended with live SNMP agents, hardware packet capture, and firewall 
integration. 
Keywords: Network Management System, Topology Discovery, Device Role Mapping, Weka 
J48, Decision Tree, Cytoscape.js, Spring Boot, Cyber Defense, Real-Time Telemetry.

CHAPTER 1: INTRODUCTION 
1.1 Background 
Modern enterprise communications, cloud-native datacenters, and real-time 
collaboration environments rely on sophisticated multi-tiered network topologies comprising 
routers, multi-layer switches, physical servers, wireless access points, and client workstations. 
These communication infrastructures facilitate critical business operations, distributed 
computing, and high-bandwidth data transfers. However, as enterprise networks scale, network 
administrators face significant hurdles in discovering device topologies, verifying device roles, 
and detecting misconfigured or deceptive endpoints. 
Traditional Network Management Systems (NMS) depend heavily on static protocol 
polling (such as SNMP or CDP/LLDP) and manual diagramming. When networks expand or 
when unmanaged, virtualized, or adversary-controlled devices are introduced, static discovery 
fails. A dynamic, machine-learning-assisted NMS capable of deducing device roles from 
topological connectivity and flow telemetry is therefore an essential operational requirement. 
1.2 Problem Statement 
Enterprise network topologies are constantly evolving with dynamic device 
attachments, routing updates, and complex cabling architectures. Manually discovering device 
roles and identifying disconnected, misconfigured, or anomalous nodes is labor-intensive and 
prone to severe configuration oversights. Existing commercial tools require costly enterprise 
licensing, complex database setups, or compute-heavy virtualization. There is a pressing need 
for a lightweight, zero-database, web-based NMS that automatically generates multi-tier 
topologies, allows interactive manual graph design, and applies explainable AI models to verify 
device roles in real time. 
1.3 Objectives 
• 
To automatically generate hierarchical multi-tier network topologies of 5 to 50 
devices with exact device counts and no isolated nodes. 
• 
To allow users to design networks manually by placing devices and connecting 
them with Copper Ethernet, Fiber Optic, or Wireless links. 
• 
To classify device roles from structural and traffic features using an explainable 
Weka J48 Decision Tree.

1.4 Scope of the Project 
The project encompasses the end-to-end design, implementation, and evaluation of a

using Java 17, Spring Boot, and Cytoscape.js, eliminating the need for physical networking

powered by Weka J48 Decision Trees trained on synthetic structural network topologies. 
Integration with live hardware SNMP agents, hardware packet capture, and physical switch 
firmware is identified as future scope. 
1.5 Literature Survey 
Decision trees are widely used for classification because their rules can be read and 
verified by a human. The C4.5 algorithm (Quinlan, 1993) builds a tree by repeatedly splitting 
the data on the attribute with the highest information gain ratio, and the Weka J48 classifier is 
an open-source Java implementation of it (Witten et al., 2016). Ensemble methods such as 
Random Forest (Breiman, 2001) can improve accuracy, but a single tree is easier to explain, 
which suits a tool whose output must be justified to a network administrator. 
Machine learning has also been applied to network traffic analysis. Surveys of traffic 
classification techniques describe how flow-level statistics can be used to identify traffic 
classes (Nguyen and Armitage, 2008), and deep learning has been explored for network 
intrusion detection (Javaid et al., 2019). Such work concentrates mainly on classifying traffic 
rather than the devices that produce it. For visualization, Cytoscape.js provides a graph theory 
library for rendering and analysing network graphs in the browser (Franz et al., 2016), and 
simulation tools such as Cisco Packet Tracer and GNS3 are commonly used to design and study 
topologies (Cisco Systems, 2023). 
The present project combines these ideas. It uses an explainable decision tree to map 
device roles from graph-structure and traffic features, and it presents the result on an interactive 
web dashboard that needs neither physical hardware nor a database.

CHAPTER 2: METHODOLOGY AND SYSTEM DESIGN 
2.1 Overall Architecture 
The system follows a modular, three-tier architecture: the Interactive Presentation Tier 
(Cytoscape.js, Bootstrap, vanilla JavaScript), the Application Control & Simulation Tier 
(Spring Boot REST controllers, NetworkSimulator, ManualDesignService, TopologyService), 
and the Machine Learning Intelligence Tier (Weka J48 Decision Tree Classifier). All data 
structures are maintained in thread-safe Java collections in memory, ensuring fast, zero-
database execution. 
2.2 Network Topology and Feature Representation 
The AI classification model evaluates devices based on eight numerical and categorical 
graph features: connection count (degree), neighbor router count, neighbor switch count, 
neighbor endpoint count, gateway connectivity (binary flag 0/1), open port count, traffic 
throughput (kbps), and packet forwarding rate (pps). These features capture both structural 
graph positioning (e.g. switches have high degree and connect to endpoints; routers connect to 
internet gateways and switches) and traffic profiles. 
2.3 Data Preprocessing and Graph Extraction 
When an automatic network is generated or a manual canvas design is submitted, the 
backend dynamically traverses the active adjacency list. It extracts direct neighbor 
relationships, categorizes adjacent node types, checks for paths to the WAN Gateway, and 
formats the vector into a Weka Instance object aligned with the pre-trained attribute dataset 
schema. 
2.4 Device Role Classification with Weka Decision Tree (J48) 
A Weka J48 Decision Tree (an open-source Java implementation of Ross Quinlan’s 
C4.5 algorithm) is trained on application startup using 200 synthetic training instances 
representing valid and anomalous device configurations. The tree recursively partitions the 
feature space using information gain ratio, producing an explainable, deterministic rule set. The 
model returns class probability distributions, from which the highest probability is extracted as 
the confidence score.

2.5 Topological Anomaly Detection and Matched/Refined Analysis 
In addition to predicting the functional role, NetMap AI performs automatic 
discrepancy analysis. If the AI-predicted role matches the configured or assigned device type, 
the status is marked as ‘Matched’ with green telemetry. If there is a mismatch (for example, a 
device labelled ‘Router’ has only one link and no gateway, or a client PC exhibits switch-like 
multi-port connectivity), the status transitions to ‘Refined’ with amber diagnostic telemetry. 
This enables security auditors to identify rogue devices, misconfigured interfaces, and 
disguised endpoints.

1. Automatic Network Generation: The user selects a device count from a discrete 
dropdown (5, 10, 15, 20, 25, 30, 35, 40, 45, 50). The NetworkSimulator computes 
the exact hierarchical distribution (Internet Gateway -> Core Routers -> 
Distribution Switches -> Servers, APs, and Workstations), assigns non-overlapping

2.9 In-Memory Thread-Safe Topology State Management 
In adherence to project requirements, no external SQL or NoSQL database is used. 
Topology nodes and edges are stored in ConcurrentHashMap and synchronized ArrayList 
collections in TopologyService. This ensures fast execution (<10ms), zero database 
configuration, and seamless local portability. 
2.10 Interactive Cytoscape.js Dashboard 
The frontend uses Cytoscape.js with the CoSE (Compound Spring Embedder) and 
Breadthfirst hierarchical layouts. Nodes are rendered using authentic Cisco Packet Tracer and 
GNS3 vector SVG iconography (Routers with 4-way circular arrows, Switches with horizontal 
arrows, Servers with rack indicators, and APs with broadcast rings). A dark cyber theme (deep 
navy panels, electric-blue accents) enhances operator focus. 
2.11 Implementation Workflow 
The implementation follows an iterative workflow. First, the Weka J48 classifier is 
initialised on application startup and trained on 200 synthetic instances that represent valid and 
anomalous device configurations. Second, the NetworkSimulator is built to generate 
hierarchical topologies for any supported device count, and the ManualDesignService is built 
to manage devices and connections placed on the canvas. Third, the role-prediction service is 
connected to both modes so that every device receives a predicted role, a confidence score, and 
a Matched or Refined status. Fourth, the REST controllers expose these services to the

3.5 Discussion 
The results show that the J48 Decision Tree maps device roles reliably across all 
supported network sizes. Accuracy stays between 98.0% and 98.5% for every device count 
from 5 to 50 (Table 3.1), so classification quality does not degrade as the topology grows. The 
Internet Gateway is classified perfectly because it is the only class with a WAN link and a 
public address. The Client (PC), Router, Switch and Server classes all reach F1-scores above 
0.97, since each has a distinctive combination of degree, neighbor types and open ports. The 
Access Point has the lowest F1-score (0.9625) and the lowest average confidence (95.8%), 
which is consistent with its overlap with other classes: it connects to a switch or router like a 
client or server, and its degree range (1 - 5) and traffic range overlap with those of endpoints 
and switches. 
The generator also met its structural targets. Every selected device count produced 
exactly that number of devices with no isolated nodes, and the hierarchical distribution of 
routers, switches, servers, access points and workstations grew in proportion to the network 
size. The Matched/Refined analysis converts raw predictions into an operational result: a 
device whose predicted role agrees with its configured type is marked Matched, while a 
disagreement is flagged as Refined for inspection. Because the J48 model returns a rule set, an 
auditor can see why a device was flagged. These figures were obtained on simulated topologies, 
so they demonstrate the pipeline and should not be read as performance on live enterprise 
networks.

CHAPTER 4: CONCLUSION AND FUTURE WORK 
4.1 Conclusion 
This project presented NetMap AI, a lightweight web-based Network Management 
System for intelligent topology visualization and device role mapping. The system generates 
hierarchical multi-tier networks of 5 to 50 devices with exact device counts and full 
connectivity, and it also lets users design networks manually on an interactive canvas. A Weka 
J48 Decision Tree classifies each device into one of six roles from eight structural and traffic 
features, reaching an overall accuracy of 98.2% on the simulated topologies, and each 
prediction is reported with a confidence score and a Matched or Refined status. All data is held 
in thread-safe in-memory collections, so the system runs locally without a database or physical 
hardware. The modular three-tier design allows each component to be replaced or extended 
independently. 
4.2 Significance of the Work 
Rapid and accurate topology discovery is critical for securing modern communications, 
preventing misconfigurations, and mitigating lateral threat movement. By providing automated 
role mapping and intuitive visual feedback without requiring expensive hardware or complex 
virtualization, NetMap AI significantly lowers the barrier for cybersecurity education, 
enterprise network auditing, and operational infrastructure management. 
4.3 Future Enhancements 
The following enhancements are planned to move the system from a prototype towards 
operational use: 
• 
Integration with live physical SNMP agents and CDP/LLDP discovery so that real 
devices can be mapped. 
• 
Integration with hardware firewall ACLs and switch firmware.

package com.netmap.ai.simulator; 
 
import com.netmap.ai.model.*; 
import org.springframework.stereotype.Component; 
import java.util.*; 
 
@Component 
public class NetworkSimulator { 
    public NetworkTopology generateTopology(int deviceCount) { 
        List<Device> devices = new ArrayList<>(); 
        List<Connection> connections = new ArrayList<>(); 
        int connCounter = 1; 
 
        // 1. WAN Internet Gateway 
        Device internet = new Device("dev-internet", "Internet", 
                DeviceType.INTERNET, "203.0.113.1", 
                "00:1B:77:AA:01:01"); 
        devices.add(internet); 
 
        // 2. Exact hierarchical distribution 
        //    (Routers, Switches, Endpoints) 
        int routerCount = Math.max(1, 
                Math.min(4, (deviceCount - 5) / 10 + 1)); 
        int switchCount = Math.max(1, 
                Math.min(7, (deviceCount - 5) / 6 + 1)); 
        int serverCount = Math.max(1, Math.min(5, deviceCount / 10)); 
        int apCount = Math.max(1, 
                Math.min(6, (deviceCount - 5) / 8 + 1)); 
        int pcCount = deviceCount - 1 - routerCount - switchCount 
                - serverCount - apCount; 
 
        // Generate Routers, Switches, Servers, APs, and Workstations 
        // Connect Internet -> Routers -> Switches -> Endpoints 
        // via Copper/Fiber/Wireless 
        updateDeviceConnectionsMetadata(devices, connections); 
        return new NetworkTopology(devices, connections, "AUTOMATIC"); 
    } 
}

Listing A.4: Manual Canvas & Validation Service (ManualDesignService.java) 
package com.netmap.ai.service; 
 
import com.netmap.ai.model.*; 
import com.netmap.ai.ai.DeviceRoleAIService; 
import org.springframework.stereotype.Service; 
import java.util.*; 
 
@Service 
public class ManualDesignService { 
    private final List<Device> manualDevices = 
            Collections.synchronizedList(new ArrayList<>()); 
    private final List<Connection> manualConnections = 
            Collections.synchronizedList(new ArrayList<>()); 
    private final DeviceRoleAIService aiService; 
 
    public AnalysisResult analyzeDesign() { 
        int isolatedCount = 0; 
        for (Device dev : manualDevices) { 
            if (dev.getConnectedDevices() == null || 
                    dev.getConnectedDevices().isEmpty()) { 
                isolatedCount++; 
            } 
            AIRolePrediction pred = aiService.predictRole(dev, 
                    manualDevices, manualConnections); 
            dev.setAiPredictedRole(pred.getPredictedRole()); 
            dev.setAiConfidence(pred.getConfidence()); 
            dev.setAiStatus(pred.getStatus()); 
        } 
        boolean fullyConnected = 
                (isolatedCount == 0 && !manualDevices.isEmpty()); 
        String msg = fullyConnected 
                ? "Topology successfully connected." 
                : isolatedCount + " device(s) are not connected."; 
        return new AnalysisResult(fullyConnected, isolatedCount, 
                msg, manualDevices); 
    } 
}
